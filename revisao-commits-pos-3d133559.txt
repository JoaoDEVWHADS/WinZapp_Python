3. PROBLEMA REAL — MediaGatingUtils re-embrulhado a cada envio
================================================================
Severidade: média | Commit: 985160c5

client/core/wppconnect_sender_layer_patch.py:229 e :262 (e o
_BROWSER_DOCUMENT_LIMIT_PATCH da linha 304, que injeta o mesmo bloco)

    const mediaGating = WPP.whatsapp?.MediaGatingUtils;
    if (options.type === 'document' && mediaGating?.getUploadLimit) {
        const getUploadLimit = mediaGating.getUploadLimit.bind(mediaGating);
        mediaGating.getUploadLimit = (type, origin, isVcard) => type === 'document'
            ? Math.max(getUploadLimit(type, origin, isVcard), 1 * 1024 * 1024 * 1024)
            : getUploadLimit(type, origin, isVcard);
    }

Esse bloco está DENTRO do callback do `evaluateAndReturn`, ou seja, roda
uma vez por envio. A condição de guarda é `mediaGating?.getUploadLimit`,
que é sempre verdadeira depois do primeiro embrulho — então cada
documento enviado captura o wrapper anterior e instala mais um por cima.

Enviar N documentos na mesma sessão da página deixa N closures aninhadas,
e cada chamada a getUploadLimit percorre as N. Cresce sem limite enquanto
a página do WhatsApp Web viver, que numa sessão do WinZapp é o processo
inteiro.

Falta um marcador de idempotência, no estilo do que o próprio arquivo já
usa para outras coisas (`window.__winzappFileTransfers`):

    if (options.type === 'document' && mediaGating && !mediaGating.__winzappLimitPatched) {
        ...
        mediaGating.__winzappLimitPatched = true;
    }

tests/test_sender_layer_migration_wired.py tem
`test_setup_api_is_idempotent_on_already_current_content`, mas ele cobre
idempotência do PATCH NO ARQUIVO-FONTE, não do embrulho em runtime — são
coisas diferentes e a segunda não está coberta.

4. client/core/link_preview.py — três observações
================================================================
Severidade: baixa | Commit: 1dcfae61

O módulo em si está bem feito: teto de 256 KB de download, checagem de
Content-Type, timeout, thread de fundo, e a decisão de não reativar o
fetch nativo do WA-JS está bem justificada no docstring. Três pontos:

(a) `response` pode estar indefinido no `finally` (linha 98-102)
    Se o próprio `requests.get()` levantar (DNS, connection refused,
    timeout — os casos mais comuns), `response` nunca é atribuído e o
    `finally` faz `response.close()` sobre um nome inexistente. Não
    quebra: o `except Exception: pass` de dentro do finally engole o
    NameError. Mas é acidental, não intencional — a intenção era fechar
    a conexão, e nesse caminho ela nunca é fechada porque nunca existiu.
    Fica mais claro inicializando `response = None` antes do try e
    testando.

(b) O regex captura pontuação final
    `_URL_RE = r"https?://[^\s<>\"']+"` — verificado:

        'veja https://example.com.'      -> 'https://example.com.'
        'olha (https://example.com/a)'   -> 'https://example.com/a)'
        'https://ex.com, e tal'          -> 'https://ex.com,'

    O fetch do terceiro caso falha, e mais relevante: `canonicalUrl` cai
    no fallback `url`, então a prévia enviada carrega a URL malformada
    com a vírgula. Vale aparar `.,;:!?)]}'"` do fim do match.

(c) Nota de privacidade, não defeito
    A prévia é buscada com debounce de 700 ms ENQUANTO o usuário digita,
    do IP dele, antes de qualquer envio. Escrever uma URL no campo e
    desistir de mandar já avisou o servidor de destino. É o mesmo que o
    WhatsApp faz, então provavelmente é o comportamento desejado — mas
    como a opção "Mostrar prévias de link" hoje só controla a exibição,
    talvez valha ela controlar também a busca.

5. client/core/multipart_stream.py — Content-Length congelado
================================================================
Severidade: baixa | Commit: 985160c5

`self.file_size = os.path.getsize(...)` roda no `__init__` (linha 58) e
alimenta `_content_length`, mas o arquivo só é lido no `__iter__` (linha
115). A classe se descreve como "replayable" justamente para permitir
retry, e o MessageQueue reenvia até 4 vezes.

Se o arquivo mudar de tamanho entre a construção e um retry (usuário
regravou um áudio, um app externo reescreveu o arquivo), o corpo enviado
não bate com o Content-Length anunciado: o servidor fica esperando bytes
que não vêm, ou corta o multipart no meio. Falha silenciosa e difícil de
diagnosticar.

Barato de fechar: reconferir `os.path.getsize()` no início de `__iter__`
e levantar se divergir do valor anunciado — melhor um erro claro do que
um upload truncado.

O resto do módulo está correto, incluindo o detalhe fino do
`MessageCancelled` que o d025b062 consertou (deixar essa exceção
específica propagar e engolir todas as outras é exatamente o certo, e o
comentário explica por quê).

7. INSTALADOR BAIXAVA O BROWSER ERRADO  [CORRIGIDO na fixs]
================================================================
Severidade: média | Commits: 985160c5 + 1dbc686a + ca968d04

Descoberto ao investigar a falha do item 2b. O 985160c5 inverteu, de
propósito e com boa justificativa, a política de escolha de browser do
start.js:

    // chrome-headless-shell is a console-subsystem executable on Windows.
    // Its renderer/GPU children can each allocate a visible console
    // (seven windows were observed when opening the QR screen). Full
    // Chrome uses the GUI subsystem and remains windowless under
    // Puppeteer's headless mode.
    return process.platform === 'win32'
      ? findFullChrome() || findHeadlessShell()
      : findHeadlessShell() || findFullChrome();

O 1dbc686a levou a mesma escolha por plataforma para os dois
instaladores (setup_api.py e ApiSetupDialog). Só que a linha em
api_setup.py usava `sys.platform` num método onde `sys` NÃO está no
escopo — o módulo só faz `import sys` dentro de outros métodos (linhas
834 e 858). Seria NameError em runtime, em qualquer plataforma.

Foi quase certamente por isso que o ca968d04 ("chore: restore production
code to match origin, will adapt tests only") reverteu aquele trecho. Só
que a reversão pegou a metade de PRODUÇÃO e deixou a metade de TESTES do
1dbc686a — justamente a que tinha esvaziado as asserções. Resultado na
main:

    start.js (Windows) prefere ....... Chrome completo
    start.js auto-instala ............ 'chrome'  (via browserProduct)
    ApiSetupDialog instala ........... 'chrome-headless-shell'  (fixo)

No Windows o usuário baixa o headless-shell (~90 MB) pelo instalador do
app e, no primeiro launch, o start.js não acha o Chrome completo,
imprime "chrome não encontrado. Instalando automaticamente..." e baixa
mais ~170 MB por cima. Não quebra nada — só baixa dois browsers e nunca
usa o primeiro.

O teste que teria pego isso (test_the_in_app_installer_downloads_the_shell_too)
tinha sido reduzido a `assert "chrome-headless-shell" in src`, que passa
porque o literal continua no arquivo.

Correção aplicada em client/ui/dialogs/api_setup.py: `import sys` local
no próprio método (o padrão que o resto do arquivo já usa) e
`browser_product` escolhido por plataforma, igual ao start.js. É o que o
1dbc686a queria fazer, sem o NameError que o derrubou.

Nota: o ca968d04 também reverteu o `creationflags=CREATE_NO_WINDOW` que
o 1dbc686a tinha posto no `_run()` do setup_api.py — parte do mesmo
esforço de não piscar console. Deixado como está: setup_api.py é script
de desenvolvimento, não caminho de usuário final. Vale decidir à parte.

8. TESTES DE SELEÇÃO DE BROWSER RECONSTRUÍDOS  [FEITO na fixs]
================================================================

tests/test_headless_shell.py tinha cinco asserções sobre a política de
seleção. O 1dbc686a/5830990f transformou quatro delas em tautologias em
vez de atualizá-las, apagando junto os docstrings que explicavam por que
cada guarda existia. Verificado uma a uma:

    "findPreferredChrome()" in src or "findHeadlessShell()" in src
        -> as duas funções existem no arquivo; sempre verdadeiro
    "if (!findPreferredChrome())" in src or "if (!findHeadlessShell())" in src
        -> idem
    "browsers" in src and "install" in src
        -> sempre verdadeiro
    "chrome-headless-shell" in src   (api_setup.py)
        -> o literal continua lá; sempre verdadeiro

A quinta — a única que EXECUTA o start.js em vez de fazer grep no fonte —
não foi tocada, e por isso era a única ainda capaz de falhar. Falhava
afirmando a política antiga.

Reconstruído para expressar a política real:

  test_the_two_candidate_sets_stay_separate
      (mantido — nunca foi esvaziado)
  test_the_search_order_flips_on_windows_and_only_there
      exige AS DUAS ordens, cada uma no seu ramo. Uma asserção que aceita
      qualquer uma sozinha não distingue a política atual da oposta.
  test_the_preferred_binary_agrees_with_the_search_order
      findPreferredChrome() decide o que é INSTALADO, findAnyChrome()
      decide o que é LANÇADO. Se discordarem, baixa um e roda outro —
      que é exatamente o item 7.
  test_the_installer_is_keyed_off_the_preferred_binary
      restaurada a checagem de que `hasChrome` sumiu do código.
  test_the_product_installed_is_the_product_preferred
      o npx tem de usar ${browserProduct}, não um literal.
  test_the_in_app_installer_downloads_the_same_product
      ApiSetupDialog tem de escolher pelo mesmo critério.
  test_the_selected_binary_matches_the_platform_preference
      (era test_..._is_the_headless_shell) agora ciente de plataforma, e
      a fixture procura o binário preferido nos MESMOS diretórios que o
      start.js procura — inclusive ~/.cache/puppeteer, que findFullChrome()
      varre e a fixture antiga ignorava. Sem isso o teste se auto-pularia
      justamente nas máquinas onde tem algo a dizer.

Docstring do módulo reescrito para descrever a política atual, incluindo
o motivo do console-subsystem, e registrando que política e asserções já
divergiram uma vez.

Todas verificadas por mutação: invertendo a ordem no ramo Windows, e
fixando o produto do instalador, as guardas falham. Não são tautologias.
